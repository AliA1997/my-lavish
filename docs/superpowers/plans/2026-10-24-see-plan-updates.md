# see-plan Updates Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rename the CLI to `see-plan`, let it open Markdown plans, let the human start a fresh session after ending one, launch Claude in PowerShell from the page, and show that Claude session's transcript in the side panel.

**Architecture:** All changes extend the existing pieces: `src/cli.js` (commands), `src/server.js` (Express + WebSocket), `src/session-store.js` (state.json), `src/chrome-page.js` + `public/chrome-client.js` (side panel). Two new focused modules: `src/plan-markdown.js` (Markdown to HTML) and `src/claude-launcher.js` + `src/claude-log.js` (start Claude, read its transcript). Side effects that tests can't run (spawning PowerShell) are injected into `createServer` so tests pass a fake.

**Tech Stack:** Node 22 ESM, Express 5, ws, chokidar, `node --test`. New dependency: `marked@^15` (Markdown to HTML).

**Spec:** The user's request, kept verbatim here:
> - Ability to create a new session after ending the session.
> - Automatically connect to your claude agent or have a button to connect to your claude. — Opens powershell, then runs the "claude" command.
> - Convert plan markdown files to a html artifact (if it doesn't already)
> - Looks claude session logs via a session id provided by claude.
> - Change the command in PATH environment variable to "see-plan <plan file>"

## Decisions made for you (review these)

1. **"New session"** = same file, fresh conversation: chat is cleared, status goes back to `open`, `ended_by` and `claude_session_id` are dropped. Feedback the agent has not collected yet (from **Send & End**) stays queued so nothing is lost. The existing `--reopen` (resume with history) is unchanged.
2. **Connecting Claude** is a **Connect Claude** button in the panel (shown when no poll is listening), plus an opt-in `--with-claude` flag on `see-plan <file>` that does the same thing automatically. Windows only; elsewhere the server answers `UNSUPPORTED_PLATFORM`.
3. The launched Claude is started with `& $env:SEE_PLAN_CLAUDE --session-id <uuid> $env:SEE_PLAN_PROMPT`, so the server *knows* the session id without asking Claude. The Claude path and the prompt (which contains the plan path) travel only in environment variables, never in the script text. An agent that is already running can provide its own id with `--claude-session <uuid>` on `poll` or `open`; the panel also has a field to paste one.
4. **Markdown**: `see-plan plan.md` writes `plan.html` next to it if it does not exist, and rewrites it when the `.md` is newer **only if** the existing `.html` was generated by see-plan (it carries `<meta name="generator" content="see-plan">`). A hand-written `plan.html` is never overwritten. `poll`/`reply`/`end` accept the `.md` path too, and `poll` regenerates first, so the agent can edit the `.md` and the page reloads.
5. **Rename**: only the binary name changes (`see-plan`). The package name, the `/health` `app` value (`my-lavish-axi`), the `MY_LAVISH_*` env vars and `~/.my-lavish-axi` state dir stay, so running servers and existing state keep working.
6. **The `.md` is the file agents edit.** A Markdown session stores `source_file` (the `.md`); `poll`'s `next_step` and the Connect Claude prompt name the `.md`, never the generated `.html`. Opening a see-plan-generated `.html` that has a sibling `.md`/`.markdown` is treated as opening that `.md`, so edits are never made to a file that the next regeneration overwrites.

## Review Focus

1. **Hostile file paths in the PowerShell launch** (`C:\Users\O'Brien\x’; calc; ’\$(calc)\plan.md`): PowerShell also treats `‘ ’ ‚ ‛` as single quotes, so no path text may enter the script; Claude must still receive the exact path. Pinned in Task 4 (`buildClaudeLaunch keeps paths out of the script`).
2. **A hand-written `plan.html` beside `plan.md`** must never be overwritten. Pinned in Task 2 (`never overwrites a hand-written html`).
3. **Transcript being written while read**: the last line can be half-written JSON; it must be skipped and re-read next time, not lost. Pinned in Task 5 (`partial last line is not consumed`).
4. **Double-clicking Connect Claude** must not open two Claude windows. Pinned in Task 4 (`second connect within 60s is refused`).
5. **Starting a new session while Send & End feedback is still queued** must not drop that feedback. Pinned in Task 3 (`new session keeps queued prompts`).
6. **Multi-MB transcripts**: no `claude-log` response may exceed 256 KB, and no request may read more than that from disk. Pinned in Task 5 (`reads at most maxBytes per call`).
7. **Presence updates must not delete the Connect Claude button** (`setPresence` used to overwrite the banner's `textContent`). Pinned in Task 4 (`presence text has its own span`).
8. **Agent edits to a Markdown plan must not be lost on regeneration.** Pinned in Task 2 (`opening generated html maps back to its md`, `poll next_step names the md`).

## Performance

- **Expected load:** one person, one or two sessions open at a time, Claude transcripts up to several MB (5.3 MB seen in practice).
- **Budget:** each `GET /api/:key/claude-log` returns at most 256 KB and reads at most 256 KB from disk (positioned `fs` reads, never `readFile`). The panel keeps at most 500 log entries in the DOM. Measured by the multi-MB fixture tests in Task 5.
- **No `state.json` on the log hot path:** the server keeps `Map<key, { claudeSessionId, transcriptPath }>`; `claude-log` (polled every 2 s) reads only this map once it is filled.
- **Nothing blocks the event loop on a request:** `findClaude` uses async `execFile` and caches a found path for the process lifetime; no `execFileSync` in request handlers.
- **Already fine (no change):** regenerating on poll cannot loop because the watcher compares content hashes (`src/artifact-watcher.js:59`); the transcript-dir scan is cheap and its result is cached.

## Security

- **Launch hardening (Task 4):**
  - Spawn `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` and `%SystemRoot%\System32\where.exe` by absolute path, never by bare name. Node looks in `cwd` before PATH, so a planted `powershell.exe` in a plan folder would otherwise run.
  - The launch script is a constant apart from the server-generated, validated UUID. The plan path and the Claude path reach it only through `SEE_PLAN_PROMPT` and `SEE_PLAN_CLAUDE` in the child's `env`.
  - `claude` is resolved once by `findClaude`: prefer `.exe`, then `.cmd`, never `.ps1` (the default execution policy blocks it).
  - Claude starts in the plan's repo root (nearest ancestor containing `.git`, found by walking up, with no process spawned), or in the plan folder when there is none.
  - Never pass `--dangerously-skip-permissions` or any other permission-bypass flag. Claude's own workspace-trust prompt is the gate for that folder's `.claude/settings.json` hooks and `.mcp.json`.
- **Launch abuse:** at most one pending launch across the whole server (keys are free to create, so a per-key limit caps nothing).
- **Transcript access (Task 5):** `findTranscript` checks the id against the UUID regex again itself, not only at the POST. `after` is clamped to a whole number ≥ 0. Log entries are rendered with `textContent` only, never `innerHTML`: tool output is untrusted, and the chrome page shares an origin with `connect-claude`.
- **Browser surface (already fine):** the Host allowlist (`src/server.js:148`) and origin guard (`src/server.js:156`) block cross-site and DNS-rebinding calls. Plan HTML, including `marked` output, renders in a sandboxed iframe with an opaque origin and cannot call the API.
- **Accepted risk: every local process is trusted.** The server binds `127.0.0.1` with no token, and any process can forge an `Origin` header. So any local process, including one under another Windows account, can attach a session id and read that Claude transcript, or trigger a launch. **Why accepted:** existing endpoints already work this way, and anything running as the user can read `~/.claude` directly. Revisit if see-plan is ever used on shared machines (fix: a per-server token in the state dir, required on header-less calls).

  - `findTranscript(sessionId, { claudeDir }): Promise<string | null>` — first re-checks `isClaudeSessionId(sessionId)` itself (returns null if it fails, so no caller can turn it into path traversal), then scans `<claudeDir>/projects/*/` for `<sessionId>.jsonl`; returns null if absent.
  - `summarizeLine(obj): Array<{ role: "user"|"assistant", kind: "text"|"tool_use"|"tool_result", text: string, at: string }>` — only `type` `user`/`assistant` with a `message`, skipping `isMeta: true`. String content → one `text`. Array content: `text` blocks → `text`; `tool_use` → `kind: "tool_use"`, text `` `${name} ${JSON.stringify(input)}` ``; `tool_result` → `kind: "tool_result"`, text from its string content or joined text blocks; `thinking` and others skipped. `text` truncated to 2000 chars with `…`. `at` = `obj.timestamp`.
  - `readTranscript(path, { after, maxBytes = 256 * 1024 }): Promise<{ entries, next, omitted }>`. `after` and `next` are byte offsets.
    - Reads with `fs.promises.open` + `filehandle.read` at a position, never `readFile`, and reads at most `maxBytes` per call.
    - **Tail mode** (`after` undefined, i.e. the panel's first load): start at `max(0, size - maxBytes)`. If that is > 0, drop everything up to and including the first `\n` and return `omitted: true`.
    - If `after > size` (the file was replaced or truncated), restart in tail mode.
    - Only consumes through the last `\n` in the chunk, so a partial last line is left for the next read. Unparsable complete lines are skipped.
    - If a full `maxBytes` chunk contains no `\n` (one line bigger than the cap), `next` moves past the whole chunk. The rest of that line then fails to parse on the next read and is dropped, so the reader never gets stuck.
  - `createServer({ ..., claudeDir })` option, default `process.env.CLAUDE_CONFIG_DIR ?? path.join(os.homedir(), ".claude")`.
  - Server-side `claudeLinks: Map<key, { claudeSessionId, transcriptPath: string | null }>`.
    - Filled by `connect-claude` and `claude-session`.
    - On the first `claude-log` request for a key the map lacks, filled once from `getSession`.
    - `transcriptPath` is cached on the first `findTranscript` hit.
    - `claude-log` never reads or parses `state.json` once the key is in the map.
  - `GET /api/:key/claude-log?after=<n>` (refuse `isCrossSite`) → `200 { claude_session_id, found, entries, next, omitted }`.
    - `after` absent → tail mode. Present → `Math.max(0, Math.floor(Number(after)) || 0)`.
    - `claude_session_id: null, found: false, entries: []` when none is set.
  - `POST /api/:key/claude-session { id }` (JSON; header-less or same-origin) → validates, stores, updates `claudeLinks`, broadcasts `{ type: "claude-session", id }`, `200 { ok: true }`.

    - An invalid id → `VALIDATION_ERROR` before any network call.
